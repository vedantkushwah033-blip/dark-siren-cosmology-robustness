# Integration audit: inclusion-posterior quadrature and shared H0 likelihood

**Status:** source-level integration review; no multi-event calibration or coverage result is claimed.  
**Target branch:** `research/inclusion-posterior-quadrature-prototype`  
**Scope:** synthetic low-redshift Euclidean methodology only.

## 1. Review update

The first version of this note recorded the pre-integration base-branch API. The target branch has since added:

- `src/dark_siren_robustness/shared_inclusion_likelihood.py`
- `src/dark_siren_robustness/h0_posterior.py`
- corresponding tests.

The earlier statement that the target branch had no shared multi-event likelihood is therefore superseded. This revision reviews the new implementation and its remaining validation gap.

## 2. Implemented shared-node likelihood

`shared_inclusion_selected_log_likelihood` now:

1. Takes one validation-posterior quadrature object, a fixed discrete catalogue, and multiple event records.
2. Builds node-specific normalized host weights from the same inclusion-probability nodes:
   `w[j,k] ∝ base_weight[j] / pi(z[j]; theta[k])`.
3. Computes each event's raw Gaussian host-mixture log likelihood conditional on each shared coefficient node.
4. Sums event log likelihoods at fixed node k.
5. Computes a node-specific one-sided detection efficiency from those same host weights.
6. Subtracts `N_events * log(beta)` at each node.
7. Marginalizes the joint selected likelihood once over the validation-posterior node weights using log-sum-exp.

This is the correct shared-nuisance factorization for its declared common-noise, common-threshold, fixed-size toy sample. It does not independently marginalize each event. The optional `population_base_weights` are part of the population-mixture assumption and must be declared and matched to the generator.

`normalize_h0_posterior` then applies the uniform H0 prior and normalizes the already marginalized log likelihood. Its boundary interpolation is a useful improvement over silently truncating the prior interval to interior grid points.

## 3. Selection-rule compatibility: the critical remaining gate

The new shared-likelihood function explicitly implements a **one-sided** selection rule:

```
d_obs >= detection_threshold_mpc
beta(H0; theta_k) =
    sum_j w[j,k] * Phi((c*z[j]/H0 - threshold)/sigma).
```

This agrees algebraically with the one-sided `dataset_likelihood.event_detection_efficiency` helper, which also uses `P(d >= threshold)`.

It does **not** agree with `scripts/run_selected_likelihood_sbc.py`, whose generator and inference use the finite open interval

```
DETECTION_MIN < d_obs < DETECTION_MAX
```

and whose current experiment contains one event per replicate. The finite-interval `selection.detection_efficiency_h0` and `selection.posterior_h0_selected` are a distinct model. Their results cannot be used as calibration evidence for the new one-sided multi-event likelihood.

**Correction from direct source inspection:** the repository already contains a matched one-sided multi-event population generator in `src/dark_siren_robustness/generative_selection.py`, function `generate_synthetic_population`. In one call it fixes one H0, samples parent hosts with probability proportional to the declared merger weight (1+1.5(z-z_{\min})/(z_{\max}-z_{\min})), draws common-`sigma_mpc` Gaussian distances, and retains exactly `n_detected` events satisfying `d_obs >= detection_threshold_mpc`. The existing `scripts/run_synthetic_selection_experiment.py` writes separate observable and truth tables. This is the correct one-sided multi-event generator family for the new likelihood; the earlier statement that no such generator existed was incorrect.

The remaining integration gap is narrower:
- The current smoke runner generates one analysis parent/catalogue/event sample, but it does not yet generate a second independent validation parent frame and pass a validation sample to the inclusion fitter.
- An independent validation frame can be generated by a second call to `generate_synthetic_population` with a distinct seed and the same DGP settings, then sampled with `split_disjoint_validation`; only its validation redshifts and retention labels should enter the fitter.
- The prototype branch now adds `n_generation_attempts`, `n_detected_candidates`, `n_rejected_candidates`, and `n_excess_detected_candidates_discarded` to the generator config, with arithmetic invariants covered by `tests/test_generative_selection.py`. The runner writes this config alongside the observable/truth tables. However, candidate-level rejected draws are not yet exported, so an independent auditor cannot reconstruct these counters from raw attempt records; add an attempt-level generation trace before treating the counters as independently audited.
- The generator's sigmoid-with-floor inclusion law is not exactly the polynomial-logit model fitted by the new module. That is a deliberate misspecification stress case, but it must be declared and must not be described as a correctly specified degree-1/2 benchmark.
- The generator uses the merger weight above, so the caller must pass the matching function of the analysis-catalogue redshifts through `population_base_weights`.

Thus the one-sided selection rule and common-noise assumptions are source-matched, but the independent-validation orchestration, attempt/rejection provenance, end-to-end raw-artifact audit, and calibration remain incomplete. Do not use the finite-interval one-event SBC results as evidence for this different one-sided multi-event model.

## 4. Existing test coverage and missing tests

The target branch currently has tests for:
- node-specific host-weight normalization and diagnostics;
- independent reconstruction of per-node multi-event log likelihoods;
- independent reconstruction of one-sided beta from the same node-specific weights;
- shared-node log-sum-exp marginalization;
- normalized H0 posterior construction;
- rejection of heterogeneous event noise under the common-beta implementation;
- rejection of events below the one-sided detection threshold.

The following regression tests were added to `tests/test_shared_inclusion_likelihood.py` after the initial review:
1. **Event-order invariance** of node-conditional and marginalized likelihoods.
2. **Joint node-order invariance** when nodes and their posterior weights are permuted together.
3. **Single-event reduction** against the existing one-sided `dataset_likelihood.event_log_likelihood`, `event_detection_efficiency`, and `selection_conditioned_log_likelihood` helpers.
4. **No-selection limit** with a high-acceptance regime where beta tends to one and selected/unselected joint likelihoods agree.
5. **Full shared-node factorization adversary** showing the shared-node marginal differs from the incorrect sum of event-wise marginalized likelihoods.

These tests are committed but have **not** been executed locally or verified by current-head CI in this session.

Still required before a scientific result:
1. **Independent finite-host enumeration** in a tiny catalogue, with calculations implemented separately from production helpers.
2. **Matched multi-event prior-predictive generator and raw-artifact auditor** for the exact one-sided threshold and common-noise model. The existing finite-interval, single-event SBC runner is not a match.
3. **H0 grid refinement after node marginalization:** compare final posterior densities and quantiles on nested grids.
4. **Quadrature refinement after likelihood propagation:** compare the final H0 log marginal likelihood across orders, not just coefficient moments/evidence/predictions.
5. **Prior-scale sensitivity:** halve/double slope prior scales and quantify effects on host weights and H0 posterior.
6. **Failure accounting:** preserve non-converged quadrature, invalid beta, underflow, and optimizer failures as explicit non-success attempts.
7. **Population-model justification:** verify the base weights and fixed catalogue used for beta represent the same declared event-generating population.

The current tests establish algebraic consistency and several invariance/limiting-case properties of the primitive. They do not establish a matched multi-event generator, calibration, coverage, or robustness across the planned design.

## 5. Source-level cautions

- The new function rejects heterogeneous event noise because its selection denominator uses a single common sigma. This is explicit and preferable to silently applying one beta to heterogeneous events.
- The event distance is checked against the one-sided threshold, but the inference function alone cannot establish that the data were generated by that exact rule.
- The node-specific weights used for event likelihood and beta are derived from the same log-weight matrix, which avoids a separate normalization mismatch.
- The optional base weights must be justified as population mass/rate weights, not tuned after looking at H0 results.
- A high quadrature ESS is not proof of quadrature convergence; final H0 likelihood stability is a separate requirement.
- The modular/cut interpretation remains: validation data determine the inclusion-coefficient posterior; GW events do not update those coefficients.
- The construction is not an event-rate likelihood and does not establish a real detector selection function or real survey completeness model.

## 6. Decision

**Software direction: conditional GO.** The target branch contains a mathematically coherent shared-node multi-event likelihood primitive, and the repository contains a matched one-sided multi-event generator. The one-sided selection and common-noise assumptions are source-matched.

**Calibration direction: NO-GO for confirmatory claims.** First orchestrate an independent validation frame alongside the analysis population, record generator attempt/rejection provenance, complete the missing adversarial/limiting-case tests, add downstream H0 quadrature convergence, and independently audit a smoke artifact. Until then, describe this as a source-level likelihood prototype with unit-level algebraic tests—not as validated H0 posterior propagation.

No LVK/GWTC analysis, real observational H0 measurement, real detector validation, or universal estimator-superiority claim follows from this implementation.
